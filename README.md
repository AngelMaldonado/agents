# Agents

Agentes IA con su propia computadora (shell + Chrome) y un navegador que se ve en vivo. Herramienta interna de Cuby en `agents.cubytest.space`, sólo LAN/tailnet. El plan, las decisiones de v2 y lo descartado viven en Cuby Bubble, proyecto `agents` (README y módulo «Agents v2»).

Código: [AngelMaldonado/agents](https://github.com/AngelMaldonado/agents) (privado). Trabajo nuevo en `wip`, PRs a `main`; `v2` queda congelada mientras los entornos existentes la puedan necesitar.

## Calidad y releases

- `bun install --frozen-lockfile`: dependencias fijadas y hook Lefthook (en CI, `LEFTHOOK=0`). No requiere instalaciones globales de ESLint/Prettier/Lefthook.
- `just sanitize staged|history`, `just format check|write`, `just lint`, `just check`. El hook sólo comprueba: no reescribe ni hace staging.
- `just ci`: exige PostgreSQL `_test` aislado mediante `AGENTS_TEST_DATABASE_URL` y `AGENTS_DATABASE_URL` idénticas. Nunca apuntar a una base con usuarios.
- `just release plan`: explica sin operar. `just release`: calidad → PR/checks → merge protegido sin confirmación interactiva → dos ejecutores Komodo (`agents-app`, `agents-sandbox`) → prerelease GitHub. Sin runner ni servidor Git temporal. Nunca despliega ni migra; la preparación no ejecuta el comando de publicación.
- [Operación, activación, firma en Komodo y recuperación](release/README.md). Builds app+sandbox `linux/amd64`; clave privada Cosign sólo en Komodo. Primer baseline previsto: `v0.0.1-beta`, todavía NO publicado.
- WhatsApp está fuera del producto beta por un feature gate compartido. Se conserva código/migración para después; no se alteran los servicios ni los datos actuales.

Viene del POC **Buyer** (oct-2026), que cotizaba compras. Hoy son agentes generales sobre Postgres + DBOS: el rol de cada uno es texto libre, la conversación continúa entre tareas y responden en markdown. Sólo modelos GPT. v2 lo vuelve una plataforma de agentes generales.

## Modelos

- **Sólo GPT**: Agents no usa Claude. Catálogo inicial: **GPT-6.1 Sol** (`openai/gpt-6.1-sol`) y **GPT-6 Sol** (`openai/gpt-6-sol`); el admin puede cambiarlo, siempre con modelos `openai/`. El gateway sólo sirve `/llm/openai/v1/responses`.
- GPT usa `/v1/responses` (necesario para herramientas en GPT-6.1 Sol); pi 1.4.0 ya incluye ambos modelos en su catálogo offline.
- Con un CLIProxyAPI propio, Agents consulta `/v1/models` antes de encolar: si no ofrece el modelo del agente, devuelve un error sin crear el contenedor. Que un modelo aparezca ahí no garantiza cuota ni acceso upstream.
- Referencia: [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [GPT-6 Sol](https://developers.openai.com/api/docs/models/gpt-6-sol).

## Memoria de un agente

Cada agente tiene un volumen Docker (`agents-<instancia>-agent-<id>`, montado en `~/state`) que se conserva entre tareas:

- `pi/`: sesiones persistidas de pi, una por conversación. Cada conversación continúa entre tareas. Abrir otra explícitamente crea un contexto nuevo sin borrar el anterior; cerrar su tab sólo lo archiva visualmente. Workspace y perfil de navegador siguen siendo del agente y se comparten, con una sola ejecución activa. Canales/horarios usan siempre la conversación Principal, independientemente del tab seleccionado o cerrado. El antiguo POST vacío de reinicio sigue en 410; crear un tab exige `{requestId}` UUID. Los webhooks que solicitan `new_conversation` con un valor distinto de `false` siguen en 400 sin guardar mensajes ni ejecutar banderas antiguas.
- `work/`: `~/work`. Se conserva; `~/work/out/` empieza vacía en cada tarea y lo que el agente deja ahí son los archivos de esa tarea.
- `browser/`: el perfil de Chrome (sesiones iniciadas, cookies, almacenamiento; la caché va a `/tmp`). Quitarle un acceso del vault borra las cookies y el almacenamiento de ese origen; «Borrar perfil del navegador» lo borra entero en su siguiente tarea.

### API Keys y servidores MCP (#24)

Cada persona registra en **Configuración → Accesos** sus API Keys (la variable es el nombre: `GITHUB_TOKEN`) y sus servidores MCP, y los concede a sus agentes (también desde Herramientas del agente). Conceder agrega: no pide volver a aprobar el harness; los MCP concedidos entran a `mcp.json` y a `--tools` por `AGENTS_GRANTED_MCP`, fuera del digest (si el nombre choca, gana el del harness).

- **Proxy de salida:** una key con dominios llega al agente como marcador `agk_…` (derivado del token de proxy de la corrida). pi, su shell, sus CLI y sus MCP salen por `proxy/` (`HTTPS_PROXY=http://run:<token>@…`, CA de Agents en un bundle de `/tmp`, `NODE_USE_ENV_PROXY=1`). El proxy pide al backend las reglas de esa corrida (`GET /internal/proxy/rules`, con `AGENTS_PROXY_SECRET`) y sólo hacia esos dominios abre el TLS y cambia el marcador por el valor en los headers (incluido `Basic`). Todo lo demás pasa como túnel. Si una herramienta ignora el proxy, sólo manda el marcador. Chrome no usa el proxy (`--no-proxy-server`).
- **«Entregar el valor real»:** para lo que no es HTTP o firma con la key (AWS SigV4); el agente la puede leer.
- **Credenciales de un MCP:** sus headers y variables secretos se guardan cifrados con él y van por el proxy atados al dominio de su URL (o a los dominios que declare un MCP local). Su OAuth es por agente. Revocar o borrar cierra la sesión del agente en su siguiente tarea (`mcp_logouts`). «Probar» lista las herramientas de un MCP por HTTP desde el backend.
- **Migración:** los `agent_secrets` de cada agente pasaron a keys de su dueño (como «valor real», concedidas a esos agentes) al arrancar el server. Si una misma variable tenía valores distintos en dos agentes, se queda en cada agente marcada «por resolver» (Herramientas) hasta elegir cuál queda.
- **Dev:** `just dev` corre el proxy en reko-2 (`just proxy build`). La CA de dev vive en `data/dev/proxy` (`just dev init`). `[proxy]` en el LLM falso prueba una key `TEST_KEY` contra httpbin.org.
- **Producción:** el proxy aún no está desplegado. Sin `AGENTS_PROXY_URL`, las keys con dominios no se entregan y las de «valor real» sí.

La respuesta de una tarea es el último mensaje del agente, en markdown.

## Autonomía dentro de la computadora

La plataforma aprovisiona y aísla el entorno; el contrato y el harness aprobados delimitan el trabajo y las herramientas de pi. Creación y Automejora configuran ese harness, no administran el host.

- **Con bash**, el agente puede escribir y ejecutar scripts propios de Python/JavaScript/shell, procesar archivos e instalar dependencias locales con uv/npm en `~/work`, sin una aprobación por cada detalle de implementación. Utilidades reutilizables en `~/work/tools/`, versiones fijas y uso/dependencias documentados junto al script; dependencias en entornos virtuales o proyectos locales. No se instala globalmente ni se modifica `~/state/tools` (gestionado por la plataforma).
- **Sin bash**, no se promete ejecución ni instalación autónoma. Se usan sólo las tools habilitadas y sus restricciones; necesitar una shell sí requiere proponer un cambio de harness al dueño.
- Un script invocado por bash **no es una herramienta nueva de pi**. Escribir una extensión o skill no la carga: la carga sigue siendo explícita, sólo para tools, skills, plugins y MCP aprobados. No cambia el manifiesto, sus validaciones ni los permisos del host.
- Navegación e interacción con páginas web: navegador visible (`browser` o `agent-browser` mediante bash). APIs de servicios autorizados: MCP/CLI/scripts permitidos con los accesos existentes. Se permiten descargas de dependencias; no se permite eludir bloqueos, extraer sesiones del navegador ni concederse nuevos accesos.
- Se mantienen usuario sin root, aislamiento de red, límites de CPU/RAM/tiempo/costo y manejo de secretos. Scripts y dependencias tienen los mismos permisos del proceso; no son otra frontera de seguridad. Si faltan paquetes del sistema o accesos, el agente informa y pide ayuda, no improvisa administración privilegiada.

Este ajuste es de prompts (`server/src/prompt.ts`, `sandbox/harness.ts`, `server/skills/grill-me.md`), sin cambios de imagen base ni de provisionamiento. La inicialización sigue sin turno LLM y no acredita funcionamiento de CLI/MCP ni de dependencias externas sólo porque pase la sonda del harness. Las pruebas de regresión del prompt están en `server/src/prompt.test.ts`; no prueban por sí solas el comportamiento de un modelo real.

## Agentes compartidos y estado «Ocupado»

El dueño comparte el agente con otras personas desde Configuración → General. Quien lo recibe ejecuta tareas y consulta el trabajo, pero no configura, usa Automejora, ve el prompt ni toma el control del navegador. Las conversaciones, el workspace y las sesiones siguen siendo compartidos; esto no crea contextos privados por usuario. Las corridas consumen la cuenta GPT y la cuota del dueño.

Cada ejecución atiende a una persona: sus seguimientos se incorporan a su tarea; los mensajes de otras personas quedan pendientes hasta que termine, en orden de llegada. La vista muestra **Ocupado con la tarea de…** y permite dejar el siguiente encargo sin interrumpir. Una solicitud de ayuda ajena no captura ese encargo como respuesta. Sólo el solicitante o el dueño responden/dirigen/cancelan la tarea; un admin conserva la cancelación. Quien lo tiene compartido sólo puede quitar o enviar ahora sus propios mensajes de la cola; el dueño puede manejarla entera. El solicitante se deriva del mensaje inicial persistido (`requested_by`), sin cambiar `runs.person_id` ni requerir migración.

`just dev sharing` verifica por HTTP con tres usuarios ficticios, GPT simulado y pi/Chrome/DBOS reales: exclusión entre personas, permisos, cola, orden de ejecución y recuperación después de reiniciar la API. Usa su propia base, contenedores y volúmenes temporales y los elimina al terminar; no usa cuentas GPT reales ni cambia el routing compartido de dev.

## Canales

Un agente despierta por la web, por su **webhook de entrada** (`POST /hooks/<token>`, firmado con HMAC: `X-Agents-Signature: t=…,v1=…`) o por sus **horarios** (cron de DBOS, hora de `America/Mexico_City`). Todo entra a su buzón (`server/src/inbox.ts`): si duerme, empieza una tarea; si está trabajando, es un seguimiento; si está atascado, es la respuesta. Cuando una tarea termina o se atasca, su **webhook de salida** recibe la respuesta, enlaces firmados de 7 días a los archivos y el `context` del puente, con reintentos durante ~24 h (`server/src/channels.ts`). Los webhooks se configuran en **Configuración → Canales** y la agenda en su propia pestaña **Configuración → Horarios**, dentro del mismo modal. Canales y Horarios son secciones directas, sin cards envolventes; el contenido de las pestañas usa ScrollArea de shadcn. La agenda usa **FullCalendar Standard 6.1.20 (MIT)**, con vistas Mes/Semana/Agenda, creación visual diaria/laborable/semanal/mensual y cron avanzado. Luxon y cron-parser proyectan los disparos en la zona del horario; DBOS sigue ejecutándolos. Los bloques no indican duración, no se arrastran y las acciones afectan toda la recurrencia. Elegir una fecha sólo propone el día semanal: la regla empieza a aplicar al guardar, no permite diferir su inicio ni excepciones por fecha. Los cron existentes se conservan; para cambiar una regla se crea su reemplazo y se elimina la anterior. La vista previa se limita a 200 disparos por horario y 1,000 totales, sin limitar la ejecución. El contrato completo para quien construya un puente está en Bubble: proyecto `agents`, `docs/canales.md`.

En dev, el fake-llm también es un receptor de prueba en `http://127.0.0.1:8318/hook-receiver`.

## Monitor y tiempo real

- **Por tópicos** (`server/src/hub.ts`): la galería recibe el estado de las tareas y una miniatura por segundo por agente; el stream completo (~5 fps) y los eventos de una tarea sólo llegan a quien tiene abierta la vista de ese agente, y el supervisor sólo lo manda mientras alguien la mira. Al reconectar, la web vuelve a pedir lo que se perdió.
- **Monitor** (pestaña Monitor, `server/src/monitor.ts`): cada persona ve sus computadoras (CPU, RAM, red, tiempo, costo) y su lugar en la cola; el admin ve todas, el host y los huérfanos, que puede limpiar.
- **`/metrics`** en el puerto 9464 (no pasa por Traefik): corridas por estado, cola por persona, CPU y RAM por sandbox, host, costo por persona, arranque promedio e imágenes enviadas. El panel «Agents» de Grafana y sus dos alertas viven en `~/dev/work/reko-3` (`roles/monitoring/files/dashboards/cuby/agents.json`, `roles/monitoring/files/alerting/agents.yaml`, job `agents` en `prometheus_extra_scrape_configs`).

## Crear y mejorar un agente con IA

«Nuevo agente» abre un chat centrado tipo ChatGPT, no un formulario ni dos tarjetas permanentes. Al generar un contrato aparece como artefacto markdown en un panel derecho redimensionable; en móvil o un canvas estrecho se muestra una vista dedicada con «Volver al chat». Cerrar el panel no elimina el contrato: se reabre desde su tarjeta en la conversación o desde el botón de documento del prompt. Se adapta localmente `~/dev/pi/skills/grill-me` → `grilling`: **primero entrevista, después contrato**. Las rondas de 1–3 preguntas usan **QuestionFlow de Tool UI/assistant-ui**, con elección simple/múltiple, recomendación sin preselección y «Otra respuesta» libre. Sólo se envían al pulsar Enviar respuestas; cambiar de paso no llama a GPT. Preguntas y respuestas enviadas se guardan en el mismo borrador y se recuperan por URL. El servidor exige al menos una ronda humana completa y rechaza pruebas/aprobación mientras haya preguntas; no basta un `ready: true` de GPT ni un «sí» en prosa para cerrar el formulario. No se generan contrato/harness durante las preguntas ni se abre el artefacto que oculta el chat móvil. Las selecciones/texto sin enviar se conservan al alternar modo/ancho (no al recargar). Una restauración histórica explícita sin cambios conserva su flujo de prueba/aprobación; editarla por chat vuelve a la entrevista. La copia para la aplicación vive en `server/skills/grill-me.md`; no depende del checkout de pi ni llama a Bubble.

- La UI usa **assistant-ui** (`@assistant-ui/react`) con `ExternalStoreRuntime` para conservar nuestros mensajes, API y Postgres, sin Assistant Cloud ni un backend nuevo. El compositor permite preparar el siguiente mensaje mientras espera, pero bloquea su envío hasta que termina la petición. Un fallo conserva el texto para reintentar; abrir/cerrar el artefacto o cambiar el ancho no borra el texto sin enviar. El chat y el contenido del contrato usan **ScrollArea de shadcn/Radix**, con barra visible cuando hay desbordamiento. Radix y assistant-ui comparten el mismo viewport para mantener autoscroll, lectura de mensajes anteriores y el botón de último mensaje, sin scrollers anidados. El artefacto lleva borde y esquinas redondeadas en vista compacta y dividida.
- Las reglas globales (incluida la prohibición actual de compras/pagos) no se cambian mediante el contrato. El diseñador distingue objetivo, política, capacidades reales e integraciones deseadas: pregunta si una integración faltante es requisito de activación o puede quedar pendiente, sin reducir por su cuenta el objetivo. Web/horarios/webhooks están disponibles como canales; WhatsApp está deshabilitado en la beta. MCP y CLI se declaran por agente en el harness; correo/inventario pueden requerir un MCP o puente externo y los accesos correspondientes. No se simula una conexión por mencionarla en un prompt.
- El chat usa la cuenta GPT de la persona (API key o CLIProxyAPI en Ajustes), Responses API y salida JSON estructurada. No ejecuta herramientas. El borrador y las rondas completadas se guardan en Postgres y su URL permite retomarlo. Una respuesta en curso se recupera por consulta del estado al recargar.
- Desde **Nuevo agente** y **Automejora**, la propuesta incluye **contrato + modelo + harness versionado**. El artefacto muestra Contrato, Harness, Cambios, Pruebas, Prompt completo y, en mejora, Vigente. El prompt efectivo incorpora las reglas de plataforma y el harness; el chat puede seleccionar tools y plugins publicados y generar skills de instrucciones. **Probar harness** arranca pi real en un contenedor desechable sin red, secretos ni volúmenes reales, con raíz de sólo lectura, 512 MiB/1 CPU y límite de procesos/tiempo; no llama a GPT. La prueba comprueba esquema/política, ejecutables, carga explícita de skills/plugins y tools efectivas. No evalúa calidad ni garantiza cumplir pautas semánticas. Hay una petición por persona y hasta `min(2,maxConcurrent)` pruebas simultáneas. Probar no crea un agente: sólo **Aprobar e inicializar agente** lo crea y encola su computadora persistente. El endpoint de creación directa `POST /api/agents` devuelve 409; probar y aprobar pasan por `/api/designs/:id/validate` y `/approve`.
- Aprobar es transaccional e idempotente. La comprobación entra como corrida `initialize` en las mismas colas/cuotas DBOS: contrato guardado → computadora → workspace persistente → herramientas → Chrome → listo. La barra cuenta pasos confirmados; los fallos se muestran y se pueden reintentar sin duplicar el agente. Al terminar se elimina el contenedor, no su memoria; no se mantiene una computadora ociosa ni se ejecuta un turno LLM de inicialización. Cada corrida nueva guarda una identidad UUID de workflow independiente de su número público: encolado, cancelación y señales usan esa identidad persistida. Las corridas antiguas válidas conservan sus IDs; el arranque reconcilia corridas UUID ya guardadas cuyo encolado se interrumpió, sin reproducir automáticamente trabajos legados. Un workflow antiguo no puede arrancar una corrida nueva sólo por compartir su número.
- En **Configuración**, cada agente muestra las herramientas reales, sus accesos por nombre y el prompt efectivo. **Trabajo** y **Automejora** son modos de la misma vista del agente: cambia el cuerpo desde el preview del navegador hacia abajo, no la cabecera ni sus opciones. `#/agent/<id>/improve` selecciona el modo Automejora, no monta una pantalla anidada ni un chat dentro del modal. Su borrador se conserva por URL (`#/agent/<id>/improve/<draft>`) y se puede retomar. El dueño puede conversar allí para mejorarlo; la IA recibe el contrato y resúmenes acotados de las últimas tres tareas como evidencia. Se compara la definición completa con la vigente y se aplica sólo tras probar y aprobar esa misma versión. Cualquier nueva ronda invalida la prueba. El chat no ejecuta instalaciones, concede accesos ni altera reglas globales: propone las CLI/MCP declaradas para que la plataforma las prepare al ejecutar. Con bash, los scripts y dependencias locales dentro del contrato no requieren Automejora.
- Las mejoras no se aplican mientras haya una corrida activa. Cada configuración tiene revisión; una propuesta obsoleta no sobrescribe cambios posteriores. La aprobación conserva sesión, workspace y perfil. Admin puede consultar configuración ajena, no conversar ni aprobar por el dueño.
- Una petición IA por persona a la vez, lease de 120 s, timeout de 90 s, máximo 6000 tokens de salida por petición y 20 rondas por borrador. Al alcanzar 64000 tokens acumulados no se aceptan nuevas rondas; el chat muestra el consumo de tokens. Este consumo es de la cuenta personal y es independiente del tope de costo por corrida.

### Harness y revisiones (28-oct, dev)

- Manifiesto estricto v1 compartido en `sandbox/harness.ts`: tools `read/write/edit/bash/grep/find/ls/browser/request_help/login` (ayuda obligatoria); hasta 4 skills con nombre seguro e instrucciones acotadas, hasta 8 pautas y plugins exactos `text-utils@1.0.0` (`text_stats`) y `json-utils@1.0.0` (`json_validate`). Los plugins iniciales son puros, revisados y empaquetados en la imagen; no se instala código durante la entrevista.
- `workspaceFilesOnly` comprueba rutas reales, incluidos destinos de enlaces y archivos nuevos; `readOnlyFiles` bloquea escritura y capturas a disco. Ambos requieren desactivar bash; sólo lectura también excluye write/edit. Los controles cubren las operaciones de archivos del harness confiable, no crean una frontera para código arbitrario. Browser/login gestionan su estado mediante la plataforma. **Con bash habilitado, quitar otra tool no impide operaciones equivalentes**. ## Seguridad, en corto

- El contenedor recibe un token de arranque que se quema al conectar y a cambio recibe uno de sesión, con el que se reconecta si el backend se reinicia (un deploy); muere con la corrida. Los logins de sitios viajan sólo por ese socket. pi recibe otro token que sólo sirve en `/llm/*`, para el modelo de su tarea. En la base sólo se guarda el sha256 de cada token.
- CLIProxyAPI sólo es alcanzable por el backend (red `*-internal`); los sandboxes están en otra red.
- Nadie toca el navegador ni la terminal del agente: la vista es sólo lectura; el humano hace steer o cancela.
- Los sandboxes salen a internet y a su propia red (el backend), nunca a la LAN, otras redes Docker, la tailnet, link-local/metadata ni al host. La regla es del host y vive en `~/dev/work/reko-3` (`docker_egress_lock_interfaces` y `firewall_deny_interfaces`, sobre el bridge `agents-prd-sbx`); los scripts de deploy la verifican con `scripts/egress-check.sh`. En dev (reko-2) no existe ese bloqueo. Los sandboxes resuelven DNS con resolvers públicos (`AGENTS_SANDBOX_DNS`).

- Todo está en `scripts/dev/` (`env.sh` tiene las rutas, puertos y el host de reko-2). Datos, logs y el socket del túnel viven en `data/dev/` (gitignored); borrarlo da un dev limpio.
- El sandbox llega al backend por la IP de tailnet del Mac (`tailscale ip -4`; se fuerza con `AGENTS_DEV_HOST_IP`).
- La imagen de dev es **arm64 con Chromium de Debian**: Chrome for Testing no publica Linux arm64. Producción (amd64, reko-3) sigue con Chrome; cambian user-agent y versión.
- En reko-2 **no hay firewall de salida**: los sandboxes de dev ven la LAN y la tailnet. El bloqueo de egress sólo aplica en reko-3 (producción).
- WhatsApp está apagado en dev (`FEATURES.whatsapp` y sin `AGENTS_WHATSAPP_URL`). El panel de monitor muestra 0 de memoria libre porque el server lee `/proc`, que no existe en macOS.
